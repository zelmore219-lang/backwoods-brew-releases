# Owner checklist: connect, link and activate an employee

This checklist matches Employee Employer / Backwoods Employees **0.4.4**. Install **Backwoods-Employees-Setup-0.4.4.exe** from the [Employee 0.4.4 release](https://github.com/zelmore219-lang/backwoods-brew-releases/releases/tag/employees-0.4.4), or use **App updates → Check for updates** once the verified release is published. Use the same Windows account and existing Employee data folder. Version 0.4.4 adds the five-form paper onboarding packet, Driver to shared-login creation, and authorization-code pasting; version 0.4.3 introduced the onboarding repairs below. The release includes an installer checksum and exact source/build provenance. The current signed Android 0.4.3 entry is retained; the new paper-acknowledgment screens in this release are delivered in Windows 0.4.4. Employees can complete those acknowledgments in the updated Windows app.

## What caused the messages

- **Shared Employee account service is not connected** means the current workspace is running its local draft engine without privileged shared administration. A Firebase client sign-in alone does not grant Firebase Admin access. Owner service uses a separate Google-owner connection and the existing personnel database.
- The project and public client settings are already built in: `backwoodsbrew-e3584-d52a3`. Owner service saves the Google refresh credential encrypted with Windows DPAPI in `owner-google.dpapi`. It saves the reviewed owner association and stable device ID in `owner-host.json`, under Electron's existing per-user data directory. It starts the private Python process against `records/employees-data/employees.sqlite3`, using the existing DPAPI document key. After backup and view publication succeed, the owner process publishes the public `employeeService/config` registry. Devices discover that registry; they never read the private Google credential. A fresh native sign-in now refreshes discovery even if the previous disconnected result was cached.
- **A verified UID and username mapping is required** was generated once per roster document lacking a matching document ID, `authUid`, or `username`. Main reads `usersByUid/{uid}` and the legacy `users/{username}` mirror; Wholesale reads `vendorUsers/{uid}`. Three Wholesale warnings represent three source records needing review, not proof of three link attempts or three employees. The repaired list groups the issues and identifies each document path. The owner service can verify omitted fields against Firebase Auth; conflicting fields, missing/disabled Auth users and unrelated records still require review. Listing records changes no personnel or Firebase profiles. Only the reviewed linking action repairs omitted fields and Main mirrors.
- The exact old activation error came from `identities.setup_complete != 1`. New drafts start at zero. Shared provisioning, verified linking, or local-only setup sets it to one. A local password does not establish shared application access. The server now reports all outstanding checks together instead of stopping at that first error. It still requires replacement of temporary passwords, approved non-draft required documents, verified assigned training, a job assignment, and a Firebase identity when application access is assigned.
- Payroll provider credentials, provider employee mapping, Gusto and payroll runs are **not** activation checks. Only payroll-related documents that HR actually marks required become document requirements. HR.my can remain your payroll system. The app's existing Gusto result-verification adapter remains optional; there is no automatic HR.my synchronization or HR.my payroll-finalization adapter in this change.

## Follow these steps in order

1. **Owner — open the existing records on the original Windows PC.** Confirm **People** shows the existing employee draft and its Employee ID. Keep that record; do not create another employee to retry account setup. Use the Windows account that can already open the encrypted documents. A draft stored on a different device is retained there; there is no automatic merge into the owner PC's database. Review/export it before entering a duplicate elsewhere.

2. **Owner — connect the existing Firebase project from Windows.**
   1. In [Firebase Console](https://console.firebase.google.com/), select **backwoodsbrew-e3584-d52a3**, using the Google account that owns it. Use the existing project, not a new one. If checking the console, **Authentication → Sign-in method → Email/Password** should already be enabled for existing Backwoods sign-in, and the default **Cloud Firestore** database should already exist. Do not recreate existing services or change the rules to public access.
   2. In Employee, select **Owner service → Connect or manage owner service…**.
   3. Select **Open Google owner sign-in**. In the official Firebase CLI browser flow, select **Yes, I just ran this command**, confirm the matching five-character session ID using **Yes, this is my session ID**, and continue to **Step 3 of 3 — Copy code**. Click **Copy**, return to the owner-service window, select **Paste authorization code**, then **Complete connection**. The short session ID is not the authorization code. **Edit → Paste** and **Ctrl+V** are also available. No API-key JSON, service-account key, billing upgrade, Cloud Function or Cloud Run deployment is required for this installed owner-host design.
   4. Select **Load owner records**. Choose the matching **Existing Employee owner** and **Existing Main owner**. Review the employee number and username. Check **I verified these records belong to the same owner and this PC contains the Employee data to share.** If the usernames differ, review and check the separate username-change approval only if correct. Optionally check **Start this service when I sign into Windows.**
   5. Select **Start shared Employee service** and wait for **Owner service is online**. An initial “Starting” message is not confirmation. On later starts use **Start service**; you should not need to repeat Google authorization unless it expires or Windows cannot unlock the credential.
   6. Sign out of Employee and sign in with your existing **Main username and password**. Confirm the banner says **Connected to your shared Employee workspace** and **People** still contains the same Employee ID and draft. Updated devices discover the same workspace. Keep the owner PC awake, signed into Windows and online for writes. Closing the Employee window leaves the service in the tray; **Quit and stop owner service** stops it.

   If Google authorization says this account cannot administer the project, choose the actual project owner. If the app reports Firestore permission errors, have the maintainer inspect the deployed Employee relay namespace while preserving existing Main/Vendor rules. Repository documentation records an earlier relay-rules deployment; this repair did not inspect or redeploy your live rules. The owner-service setup window connects credentials and publishes configuration; it does not deploy security rules.

3. **Owner — prepare the required paper packet on the existing employee.** Open **People → View** and confirm **Job assignments** has the right position, division, location, rate and effective date; use **Assign job → Save** only if missing. Under **Onboarding documents**, select **Prepare paper onboarding packet**. Enter the actual **Handbook version or date** and **Where completed paper forms are kept**, review the five-form checklist, check **I approve this five-form paper onboarding checklist**, and select **Approve and assign paper packet**. This publishes the paper-completion acknowledgment instructions, marks Federal W-4, Alabama A-4, Form I-9, Employee handbook acknowledgment and Emergency contact form required, and assigns all missing forms to this employee. It replaces unfinished drafts while retaining their history and signatures. Existing approved forms remain complete; other company-required forms remain required. Future hires receive the configured required packet automatically. Use **Assign required packet** to catch up another existing draft; retrying retains the same assignments. Confirm all five required forms appear and the new assignments say **Paper form + acknowledgment**. The app tracks the paper originals; it does not generate a completed official tax or I-9 form.
4. **Owner — finish the account using exactly one path.**
   - **Existing Backwoods account:** In **People → Connected Backwoods accounts**, select **Refresh connected accounts**. Find the exact verified username and UID, select **Link employee record**, choose **Employee Management access**, check the mapping-review checkbox, and select **Link existing account**. This selects an existing HR draft by exact username. If none matches, review the correct draft and username before proceeding; do not choose by display name. The existing password, application roles and Main historical IDs are preserved. Current supported application access is imported; pending local app selections are replaced.
   - **New Backwoods account:** On the existing employee profile select **Create shared login**. Enter **Initial password (12–256 characters)**, choose the required applications and roles, and keep **Employee Management portal** selected so the employee can finish onboarding. For a delivery driver, check **Driver app** and choose **Driver role → Delivery driver**; Main and Wholesale are optional for that role. A Driver manager also needs **Wholesale Vendor Ordering** selected with **Vendor role → Manager**. If Main is selected, enter the actual **Existing Main store ID**. Find it in Firebase **Firestore Database → Data → appData** collection → **main** document → **stores** array → the matching store's **id** field; never substitute the HR location ID or guess a store. Select **Provision shared account**. Deliver the temporary password through your approved secure channel.
   - **Add Driver to an existing shared login:** On the same employee profile, use **Application access → Assign access → Application → Driver app**, select **Application role → Delivery driver**, then **Save**. This preserves the existing username, password and other approved grants. Confirm the Driver application row is **active**, then use that same Backwoods login in Driver. If Driver payroll time is needed, separately review its actual Delivery job in **Time & attendance → Shared time cards**; application access does not choose a payroll job.
   - **Confirm:** **Onboarding progress** shows **Shared Backwoods identity: linked**, and the requested **Application access** rows show active. The existing draft retains its Employee ID. Use the same employee record when retrying. A completed provisioning retry does not reset its password; linking retries use unique UID and employee/application keys rather than adding duplicates.

5. **Employee — sign in and replace any temporary password.** Use Employee Management with the shared Backwoods username/password. If prompted, use **Change my password → Change password**, then sign in again with the new password. An existing linked account keeps its existing password unless it already requires a reset. Confirm the password requirement disappears from **Onboarding progress**. Main time cards continue using the existing Backwoods sign-in.

6. **Employee, then owner / HR / authorized verifier — complete paper forms and app acknowledgments.** Give the employee the current official Federal W-4, Alabama A-4 and Form I-9, your approved handbook/paper acknowledgment and emergency contact form. The employee fills out and signs their part on paper, returns it to owner / HR, and updates emergency details under **My workspace → Update contact details**. In **My workspace**, the employee opens each required assignment using **View → Acknowledge paper completion**, types their full name, checks the paper-completion declaration and electronic-signature consent, then selects **Sign acknowledgment**. Signing here records that they completed their paper portion; it does not replace it. No upload is required for the paper workflow.

   A different owner / HR reviewer opens **Documents → Review**, checks **I reviewed the completed and signed paper original**, enters **Paper file reference / storage location**, and selects **Approve document**. Form I-9 also requires the authorized verifier's **Verification procedure**, Section 1 and Section 2 dates, examination/eligibility evidence, examination/eligibility confirmations and verified retention date. Keep its completed official original in the restricted I-9 file. Store the other paper originals in the proper personnel/confidential files; do not enter SSNs or bank details into the file-reference field. Confirm each required assignment is **approved**. Older electronic/upload workflows remain available for other templates and retain their existing original-file requirements.
7. **Employee, then manager — finish assigned training.** Employee completes the training and selects **Training → Mark completed**. A different authorized manager opens **Training → Verify**, checks **I reviewed evidence of completed training**, and selects **Save**. Confirm the training is **verified**; **completed** alone does not pass activation.

8. **Owner / payroll administrator and employee — use HR.my for payroll onboarding.** This can run alongside steps 3–7 and is not required by the app's Activate check.
   - Owner: in **HR.my → Employee → Management**, review or add the employee with the same Employee ID, contact email and pay cycle. Invite an Employee Web Account if needed; employee completes the emailed invitation. Confirm the employee record and account are enabled. [HR.my employee guide](https://www.hr.my/doc/employee-management.html)
   - Owner/payroll administrator: configure recurring wages under **Payroll → Salary Adjustment**. For hourly pay, first define the earning item under **Payroll → Earning**. Review the configured salary and effective date. [HR.my payroll guide](https://www.hr.my/doc/payroll.html)
   - Keep tax forms, payment authorization and withholding/payment arrangements in your established Alabama payroll workflow. This repair does not establish that HR.my automatically files Alabama/federal taxes or sends employee payments. Complete required tax/payment work through your existing process.
   - Later, transfer reviewed approved time/wages into **HR.my → Payroll → Process**, review the draft, select **PROCESS**, verify the result and publish the payslip. The employee can confirm it in their HR.my Employee Web Account. There is no automatic transfer from this app; use matching Employee IDs and reconcile manually. Do not enter HR.my IDs into **Map Gusto employee (optional)** or use Gusto result verification for an HR.my payroll.
   - Employee app: **Payroll → HR.my workflow** shows these instructions. Complete the required W-4 and Alabama A-4 on paper, acknowledge completion here and have HR review the originals. No Gusto credentials or mapping are needed to activate.

9. **Owner — inspect the current activation checklist.** Open the employee profile and select **Activate employee**. Each remaining requirement identifies who completes it and where. Refreshing/opening this dialog retrieves current server state. Do not activate until all listed requirements are complete. If the owner service is offline, start it and wait for synchronization first.

10. **Owner — activate and confirm.** Check **I have reviewed required onboarding and account checks** and select **Activate employee**. The server rechecks the records. Confirm the employee's status changes from **onboarding** to **active**, the activation is in **Audit trail**, and the employee can sign in to the approved applications. Shared login/access can exist during onboarding so the employee can finish their documents; it is not itself confirmation of employment activation.
